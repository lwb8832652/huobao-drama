# 全局任务队列与并发设置设计

日期：2026-10-14；代码基线：dev / 5f84cb8。

状态：方案草案。用户已确认跨项目、全服务共用并发限制，并明确任务设置与评测任务设置分开；下述默认值与调度规则为本次建议，尚未改动应用代码。

## 目标与范围

任务列表增加与评测列表一致的设置图标入口。图片、视频、评测使用一套持久化调度机制，任务提交后立即返回编号，超过执行上限的任务等待，而不是直接调用模型。刷新页面、关闭抽屉、切换项目不影响后台执行。

本次接入普通图片与视频生成、批量分镜生成、整组宫格生成与微调、单格精修、连续性评测、AI 画面规划、宫格本地合成及视频拼接。总并发指这些后台执行单元的并发，不包含同步或流式的交互式文本写作请求，也不统计轮询、列表查询和父批次记录。界面名称使用“后台任务总并发”，避免暗示所有 HTTP 请求都受此限制。

未来新增评测类型注册自己的执行器和详情展示，默认共享评测类别的上限；不为每种评测复制一套队列。

## 当前问题与证据

- `backend/src/services/generation.ts:177`：普通任务创建为 processing，并立即执行；只有带 previsItemKey 的任务先创建为 pending。
- `backend/src/services/generation.ts:214`：分镜领取按任务类型与配置编号计数，上限固定为 2，没有全局总上限。
- `backend/src/services/previs-batch.ts:390`：批次执行另外维护按配置计数的上限 2，父条目可能先显示 processing，实际模型任务仍然 pending。
- `backend/src/services/previs-frames.ts:361`：AI 画面规划用固定并发 4。
- `backend/src/services/continuity-review.ts:419`、`backend/src/routes/previs.ts:98`：自动评测串行，手动评测等待整个执行完成后返回，不受同一调度限制。
- `backend/src/services/ffmpeg-merge.ts:70`：本地拼接创建后直接执行，没有并发限制。
- `backend/src/routes/tasks.ts:257`：删除接口直接移除记录，需要与取消执行分开，避免删除仍在上游执行的任务后失去追踪。
- `frontend/app/views/drama/episode.vue:1027`：任务抽屉没有设置入口；pending 与 processing 的汇总及行文案未明确区分。

因此只增加前端数字设置，无法实现真正的全局限流。

## 方案选择

| 方案 | 成本与限制 | 结论 |
| --- | --- | --- |
| 各 worker 增加自己的并发参数 | 修改少，但多个入口的计数仍独立；总上限、重启恢复与跨类型资源共享难保证 | 不采用 |
| 当前 SQLite 上建立统一持久化调度层 | 复用已有数据库和业务记录，统一准入、恢复、统计与取消，不新增部署服务 | 本次采用 |
| 独立消息队列与多进程执行器 | 适合未来多实例或独立执行节点，需要部署、运维和迁移工作 | 后续规模扩大时评估 |

SQLite 支持多个读事务、同一时刻一个写事务；短写事务可用于原子检查配额并领取任务。计数、状态变更和占位必须在同一事务提交，网络请求在事务外执行；数据库忙时重新领取，不绕过检查。这是结合当前部署方式的设计判断，依据：[SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)。

## 设置与默认值

任务设置和评测任务设置使用各自独立的面板、配置字段、保存操作与设置修订号。两者沿用相同的图标和视觉规范，后端执行统一调度，但不共用一个设置表单，也不互相保存或覆盖对方字段。

任务列表中的“任务设置”管理后台任务总并发、图片并发、视频并发，以及高级的 AI 画面规划、本地处理和服务商配额组。评测列表中的“评测任务设置”管理评测并发、评测队列暂停，以及原有的自动评测和关注阈值；未来其他评测类型的配置也放在此面板。

后台任务总并发为全服务上限，包含制作任务与评测任务，仅在任务设置中编辑，并明确说明作用范围。评测任务设置只读显示这个上限及其对评测的约束，不提供第二份可编辑的总上限。两个面板各自修改自己的配置，对所有项目生效。

| 所属面板 | 常用字段 | 建议默认值 | 统计口径 |
| --- | --- | --- | --- |
| 任务设置 | 后台任务总并发 | 6 | 所有接入的实际执行单元，包含评测 |
| 任务设置 | 图片并发 | 2 | 普通生图、宫格生成与微调、单格精修 |
| 任务设置 | 视频并发 | 2 | 模型生成视频，包含等待上游处理的阶段 |
| 评测任务设置 | 评测并发 | 1 | 手动、自动以及未来接入的评测类型 |

任务设置中的高级设置展开后提供 AI 画面规划并发 1、本地处理并发 1，以及可选的服务商配额组。评测任务设置保留自动评测默认关闭、关注阈值 70（范围 0–100）。默认值用于保守起步，不能代表服务商实际额度。并发整数范围统一为 1–32；暂停队列使用独立操作，不用 0 表示。

各类别上限允许相加大于总上限；每个任务开始时必须同时满足总上限、类别上限以及已配置的服务商配额上限。例如总上限为 4、图片为 3、视频为 2，当前已有 2 个视频和 2 个图片执行，则剩余图片继续排队。图片与视频没有固定保留名额，空闲资源可以共享。

服务商配额组由用户在任务设置的高级设置中关联多个模型配置，填写共享上限，解决同一账号配置多个模型后计数分散的问题；作为全局资源约束，它也适用于组内的评测模型，评测面板只读提示适用的配额。不根据 provider 名称猜测所有账号共用额度，不向客户端返回密钥。未配置配额组时仅受总上限与类别上限限制。并发不等同于每分钟请求数，RPM 等速率限制不在本次设置中承诺实现。

设置表单显示“全局设置 · 对所有项目生效”，采用数字步进输入、当前执行/上限、排队数量和明确的保存结果。自动刷新不覆盖未保存草稿。下调上限只限制后续领取，已执行任务继续；若当前执行数量高于新上限，显示“等待已有任务完成”。

## 列表与操作

- 任务列表增加与评测一致的设置图标、尺寸、位置和焦点样式；任务入口打开任务设置，评测入口打开评测任务设置，表单字段与保存操作独立。
- 列表仍只显示“进行中 / 完成 / 失败”三个可点击胶囊，重复点击取消筛选并恢复全部；不重新增加“全部”按钮。
- “进行中”包含排队和执行，旁边或列表摘要显示“执行 2 · 排队 8”。每行明确标记“排队中”“等待前置任务”“执行中”“上游处理中”“保存结果中”“需核对提交状态”等具体阶段。
- 列表与统计沿用各自当前项目、剧集或评测版本范围；全局执行、排队数据只在设置区域明确标注“全局”，不能把其他项目的任务数量混进当前列表计数。
- 排队原因优先显示实际阻塞条件，例如“视频并发已满”“服务商配额已满”“队列已暂停”。不同资源与依赖会改变启动顺序，不承诺精确总队列名次或预计完成时间。
- 排队任务可取消；失败任务可显式重试；执行中只在服务商支持并确认取消后结束，否则保留记录并继续追踪。清理记录仅用于终态任务。
- 已取消记录仍可在无筛选列表中查看，不计入完成或失败数量，保留审计信息。
- 两个面板分别提供“暂停制作队列”和“暂停评测队列”，只影响该类别尚未开始的任务，执行中继续。制作队列包含图片、视频、AI 画面规划和本地处理，暂停制作不暂停评测，暂停评测不暂停制作；各自对所有项目生效。浏览与刷新不调用付费模型。

手动评测提交改为立即提示“已加入队列 · #编号”；结果尚未完成时不能显示“评测已完成”。同一输入版本的连续点击返回同一排队或执行记录，避免重复收费。关闭自动评测停止新增自动任务，并取消尚未领取的自动任务；手动排队和已执行任务继续。

## 调度模型

增加轻量的共享执行记录，不替代 sys_task、连续性评测历史、画面规划和 video_merges 等业务表。共享记录保存 kind、项目归属、业务记录关联、状态/阶段、创建与开始/结束时间、实际配置编号、配额组、输入快照摘要、外部任务编号、提交状态及恢复信息。业务与共享记录在同一事务创建，关联键唯一。

父批次和宫格候选只聚合子任务，不占执行名额。实际的模型调用或本地处理才占一个名额；一个父批次包含十个图片任务时按实际正在执行的图片数量计数。一个模型任务的提交与轮询属于同一执行单元，不能按轮询请求增加并发计数。

原有 worker 保留业务校验、输入冻结和结果归档，移除独立的固定领取上限以及直接启动路径，统一通过调度层领取。已排队的任务冻结提示词、素材来源与摘要、模型和有效配置编号，不能在等待过程中静默切换到新的默认配置。素材使用不可变快照，或在开始时验证文件摘要；仅保存可能被覆盖的 URL 不视为冻结。服务商配置或输入不再有效时，给出明确失败原因，要求重新提交。

调度对可启动任务按类别轮转，再在该类别内按项目轮转；同一项目同一类别按创建时间和编号先后执行。轮转游标持久化，领取时原子更新。某类已满时继续检查其他类别，某项目大量批量任务不会无限阻塞其他项目；查询不能只取队头固定数量的阻塞记录而漏掉后面的可启动任务。等待依赖的任务不占名额；当前明确使用连续性依赖的流程保留前置约束，其他独立镜头不因镜号顺序被强制串行。

前置任务失败后，依赖任务标记失败并说明“前置任务未完成”，允许用户在修复后重新提交；不会无限排队，也不会自动改用另一张参考图。调度持有者租约与原子状态检查防止两个执行器同时领取，后续扩展执行器仍需遵守同一数据库配额。

## 完成、恢复与重试

业务状态采用 pending、processing、completed、failed、cancelled，并用 phase 表达等待依赖、提交、上游处理、保存结果和需人工核对等阶段。提交结果不确定时保持 processing / needs_confirmation，不显示为可直接重试的失败记录。

- 模型 POST 返回外部编号后仍占该任务的全局、类别及配额组名额，直至确认上游终态。异步视频不能在“提交成功”时释放名额。
- 上游已结束后释放服务商配额；该执行单元在下载和落库完成前仍占全局与类别名额，phase 显示保存结果。本地合成作为后续执行单元接入本地类别，父流程自身不占第二份名额。
- 保存结果失败保留可恢复的外部编号与 URL，仅重试本地下载或落库，不能重新生图或视频。
- 重启后 pending 继续等待；确定未提交的 processing 重新排队；已取得外部编号的恢复查询；提交过但没有可核对编号的保留“需核对提交状态”，继续保守占位，需人工确认上游状态后结束或重新提交。
- 领取租约到期不代表上游生成结束，不能直接释放不确定的付费请求名额并再次调用模型。
- 明确未接受的限流请求可按服务商 Retry-After 或退避策略重试，最多 2 次；状态不明的网络超时不自动重发付费提交。配置、参数、缺图和过期输入失败不自动重试。
- 取消 pending 在事务中完成，与领取互斥，保证未提交；取消已提交任务需服务商确认，否则只保留追踪，不伪装成已停止。
- 输出发布到当前画面前再次检查版本与输入摘要，过期结果保留历史但不覆盖新画面；连续性评测保持同样的历史与当前结果分离规则。

## 接口契约

- GET /settings/task-queue：任务设置所属的总上限、制作类别限制、制作暂停状态、服务商配额组、独立修订号，以及制作类别与全服务执行/排队计数。
- PUT /settings/task-queue：只校验并保存任务设置所属字段；附带该面板的修订号。请求包含评测并发、自动评测或阈值等其他面板字段时拒绝，不静默覆盖。
- GET /settings/evaluation-tasks：评测并发、评测暂停状态、自动评测与关注阈值、独立修订号和评测执行/排队计数，附带只读的服务总上限与适用配额信息。
- PUT /settings/evaluation-tasks：只保存评测设置所属字段；附带评测面板的修订号。请求包含图片、视频或服务总上限等任务设置字段时拒绝。原连续性评测设置接口作为兼容入口映射原有字段，避免产生第二份自动评测配置。
- 每个面板分别检测保存冲突，保留草稿并提示重新读取；两个面板正常同时保存各自字段时不产生跨面板覆盖。
- POST /task-queue/jobs/:queueJobId/cancel：显式取消，返回真实取消或继续追踪状态；评测、规划、本地任务由统一执行记录关联到各自业务编号，不复用可能冲突的裸数字 ID。普通任务接口需要兼容入口时，先由 sys_task 编号解析关联的 queueJobId。
- 按制作或评测作用范围提供独立暂停/恢复操作：只改变对应队列的调度开关，不改并发数，不取消执行中任务。
- 新提交接口返回业务编号、执行状态及共享任务编号；保留现有业务编号与结果查询接口，评测 POST 从等待结果改为返回已入队记录，前端随后查询进度。
- 列表在原有字段基础上补充 phase、排队原因、开始时间、是否可取消/重试等展示信息，旧客户端缺少新字段时仍能显示基础状态。

## 接入顺序与迁移

1. 建立共享执行记录、全局设置、原子领取、暂停/取消及统一恢复逻辑；通过测试验证上限与重复提交保护。
2. 将所有本次列出的后台入口接入，再移除旧 worker 的独立领取逻辑。调度不依赖前端是否打开。
3. 分别接入任务设置与评测任务设置面板及各自保存接口，调整列表排队文案、可点击筛选、评测提交响应与轮询。
4. 发布前盘点历史 pending/processing，仅为活动记录建立唯一关联；已提交的恢复查询，无法确认的保持追踪。终态历史不重跑、不批量改写。

在所有范围内入口接入前，不能宣称“后台任务总并发”已全量生效。保留现有默认关闭的自动评测，以及已有的冻结输入、历史结果和视频生成前风险确认。

## 验收

- 多项目同时提交，各类别和总量不超过已保存上限；多个配置绑定同一配额组时共享限制。
- 图片、视频与评测都有排队和执行状态；大量视频堵在队头且视频已满时，后面的图片或评测仍可利用剩余总名额。
- 同时批量提交、轮询和调度不会重复领取；父批次不重复计数。
- 两个设置面板独立保存，修改评测并发不改图片、视频或总上限，修改任务设置不覆盖自动评测与阈值；两个面板同时保存各自字段不会互相覆盖。
- 两个面板的配置跨项目统一生效；评测受到只读展示的服务总上限约束；减小上限不中断已有任务，保存冲突和未保存草稿行为明确。
- 制作与评测队列可独立暂停和恢复，互不暂停对方任务，已执行的任务继续追踪。
- 刷新、切换项目、后台重启后任务仍可查询；已提交任务不重复收费，状态不明不会自动重发。
- 取消与领取竞态不会产生“已取消却仍提交”的任务；删除记录不丢失活跃上游任务。
- 手动和自动评测共同受限制；重复点击去重；关闭自动评测不影响手动任务或已执行任务。
- 连续性依赖不占空等名额，失败可解释，过期图片与评测结果不覆盖当前版本。
- 浏览器验证两个设置入口、筛选、排队后自动开始、完成、失败重试、取消、暂停恢复和宽窄屏；使用模拟模型，不触发真实付费请求。
